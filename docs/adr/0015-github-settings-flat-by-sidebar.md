# The GitHub settings manifest is flat in Settings-sidebar order

The `github` manifest is a flat object whose keys follow the repo Settings sidebar: general fields → `access` → code/planning/automation fields → security/quality fields → `integrations` → community fields (repo files, not a Settings page). Only `access` and `integrations` stay grouped; `general`, `code_planning_automation`, `security_and_quality`, and `community` are destructured to top-level fields. Each leaf's schema description names its UI path and how conform handles it: API (checked and fixed via REST), READ (checked via REST, fix manual with the Settings path), or UI (no API: passes when off/default, otherwise skipped naming the exact Settings path). This replaces the flat v1 shape in one breaking release with no aliases (ADR 0012).

## Consequences

Authors find a field where they see it in the UI, and every blueprint field has exactly one home. Optional fields mean "not managed" and emit no result; classic `branches` protection is optional so repos protected only by rulesets do not drift. Rulesets are full objects matched by name and fixed by POST/PUT, which absorbs merge queue and tag protection (the tag-protection endpoint is gone). Interaction limits are API-fixable with the API's enum values. Check ids stay stable where the concept survives; ids for removed concepts (`tag-protection`, `required-workflows`, `merge-queue`) are dropped. Endpoints that answer 422 (public repo), 402 (billing) or 404 (feature off) skip with that reason instead of failing.

Deliberately not fields: repository name (rename breaks the target), transfer/delete (destructive), pending invitations and the interaction-limit exemption list (per-person, transient), runner registration (host-side script/token), webhook and Actions secret values (write-only), Discussions on/off fix (no PATCH field in the REST description, so it is READ), environment admin bypass fix (not in the environment PUT body, so READ), and finer UI-only detail with no API (ruleset required-reviewer teams and dismissal restrictions, classic required deployments and bypass/dismiss allowlists, prebuild schedules/notifications/optimisation, email-notification approved header, code-scanning "other tools"). Unmanaged parts of a declared ruleset are not compared.
